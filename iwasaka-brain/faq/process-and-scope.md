> [!summary] TL;DR
> 進め方は「調査→計画書→計画OK→実装」。スコープは着手前に「やる・見送り・後回し」と「これ以外はやらない」を書く。
> 束ねる基準は同じ原因か、分ける基準は関心・方針・合意相手が違うか。見送ったものは痕跡を残す。
> 見積は計画確定まで空欄、確定後も安易に増やさない。優先順位は品質・テスト・セキュリティが新機能・UX より上。

## 想定問答

**Q: このチケット、どう進める？**
A: まず現状と計画書を突合して、一旦調査だけ。計画書を出して未確定事項を yes/no に落とし、理解できないまま承認しない。「計画OK」を出すまで実装には入らない。計画と実装はセッションを分ける。→ [[iwasaka-brain/patterns/plan-before-implement|実装前に計画書を書かせる型]]
根拠: 計画書・計画承認に言及するセッションが約 110 件あり、6 月の Cursor 時代から「実装の合図が出るまで提案止まり」の運用が一貫している。

**Q: 見積はいくつにする？**
A: 計画確定まで空欄。確定したら小さめに置く。追加修正が出ても安易には増やさない。調査専用のチケットは切らない。→ [[iwasaka-brain/principles/decision-under-uncertainty|不確実な中での決め方]]
根拠: 「見積は計画確定まで埋めない」が 2026-09 と 2026-10 に再出し、「1 ポイントぐらいじゃない？多すぎない？」と SP を下げる方向の問いが観測されている。

**Q: 作業中に別のバグを見つけた。直していい？**
A: 同じ原因なら同じ PR で直す。関心が違う・方針が未決・合意相手が違うなら別チケット。見送るなら PR 本文の未対応欄か別チケット候補として痕跡を残し、気になった点は質問だけでもしておく。→ [[iwasaka-brain/principles/scope-control|スコープの切り方]]
根拠: 「同じ原因で直せる別チケットは同じ PR にまとめる」（2026-10）、「関心の異なる構造課題は別 PR に切り出す」（2026-06）が約 70 件の判断の中核。

**Q: PR が大きくなってきた。**
A: 分ける。1 PR 1 サブフェーズで、前 PR をマージしてからベースから切る。BE と FE は別コミット、生成物の再生成も別コミット。レビュアーが 1 つずつマージ判断できる大きさが上限。→ [[iwasaka-brain/patterns/ticket-and-pr-flow|チケット駆動・PR 統合の進め方]]
根拠: 2026-06 に「BE 変更は既存 PR に同梱せず別 PR」「1 PR 1 サブフェーズ」、計画書も 3 本に分けて認知負荷を下げた判断がある。

**Q: AI が頼んでいない変更まで入れてきた。**
A: 即座に戻させる。「修正量が多すぎる、全部必要な修正？」と問う。壁打ちやレビューの指摘由来でも、過剰ならスコープを戻す。スコープの最終判断は自分に置く。→ [[iwasaka-brain/principles/scope-control|スコープの切り方]]
根拠: 「AI が勝手に広げた変更範囲は即座に戻させる」「壁打ち結果に従いすぎず自分の判断でスコープを戻す」（2026-06〜07）。

**Q: 優先順位はどう決める？**
A: 品質・テスト・セキュリティが新機能・UX より上。AI の意見は聞くが決めるのは自分。順序は「いつ止めても損失が小さい順」。実施順の決定は ROI を定量化してから後回しでもいい。→ [[iwasaka-brain/principles/quality-vs-speed|品質と速度の置き方]]
根拠: 2026-09 の引き継ぎで「品質・テスト・セキュリティ ＞ 新機能・UX」を明示し、2026-08 に「いつ止めても損失が小さい順序で進める」と判断している。

**Q: 方針が決まらない論点があるが、実装は始めたい。**
A: 未決は実装から切り離す。「決めること」を先頭に置いた短い issue にして、実装側は仮値で進めて細部は別課題へ。未決を実装に混ぜると進まなくなる。→ [[iwasaka-brain/principles/decision-under-uncertainty|不確実な中での決め方]]
根拠: 「方針未決の論点は実装から切り離し短い issue にする」「仮値で進めて細部は別課題へ切り出す」（2026-09）。

**Q: 新しくチケットを起票していい？**
A: まず既存を確認して重複を疑う。「既存の範疇では」なら既存にコメントで寄せる。起票するなら起票案で止めて承認後に作成。別 issue を乱立させず、残課題は親チケットに引き継ぐ。→ [[iwasaka-brain/patterns/ticket-and-pr-flow|チケット駆動・PR 統合の進め方]]
根拠: 2026-08 に「別チケットとの違いが分かりにくい、既存の範疇では」と新規起票を却下し、起票スキルの手順を「既存確認→プラン→起票案で停止→承認後作成」としている。

**Q: マージ方式は squash でいい？**
A: squash は使わない。履歴が消える。merge commit で、PR は 1 つずつマージしてから次に進む。→ [[iwasaka-brain/patterns/ticket-and-pr-flow|チケット駆動・PR 統合の進め方]]
根拠: 2026-08 に過去の squash-merge が履歴構造の問題の原因と判明し、merge commit 必須に切り替えた。

**Q: 動作確認がまだできない。待つ？**
A: 待たない。骨組み OK で進めて後で確認するか、draft PR で前に進める。未検証は検証手段ごと PR 本文と完了コメントに引き継ぐ。省くのではなく、未検証であることを痕跡に残す。→ [[iwasaka-brain/principles/quality-vs-speed|品質と速度の置き方]]
根拠: 「動作確認が今できないなら骨組み承認で進めて後で確認」「ローカルで検証できないことは検証手段ごと PR と完了コメントに引き継ぐ」（2026-09）。

**Q: チケットをクローズするとき、何を書く？**
A: 実施内容／採らなかった案と理由／未決事項／未完なら現状と残作業、の 4 項目。issue 本文は仕様・契約、コメントは経緯・記録と使い分ける。6 行以上なら「一言でいうと」を冒頭に。ステータス変更は依頼範囲外なら触らない。→ [[iwasaka-brain/principles/communication-and-reporting|報告・共有の原則]]
根拠: 完了コメントの 4 項目構成が 2026-09 に 4 回以上明文化され、2026-09-18 には 6 件連続で同形式を要求している。

**Q: 時間が足りない。どうする？**
A: 無理に続けない。時間枠の限界で途中状態を記録して中断する。来週は BE に手を出さずフロント 1 機能、のように期間単位でも範囲を切る。精度より判断に足る概算でいい。→ [[iwasaka-brain/principles/decision-under-uncertainty|不確実な中での決め方]]
根拠: 「時間枠の限界では無理に続けず途中状態を記録して中断する」「精度より判断に足る概算で良い」（2026-09）。

## 本人が答えに迷う・保留する問い

- **小さな発見を今回スコープに入れるか切るか。** 「迷うなら今回スコープに入れて片付ける」（2026-06）と「スコープ外はその場で直さず別チケットに切る」（2026-09）が併存する。小さく同型なら入れ、関心が違えば切る、と読めるが境界は一貫していない。
- **レビューで出たセキュリティ改善を同じ PR に入れるか。** 原則は別チケットだが、優先度が高いので同じ PR で直した例がある（2026-10）。スコープ原則より先に通す場面の基準は明文化されていない。
- **一貫性のための横展開をどこまでやるか。** 「修正量より全体の一貫性を優先するかは相談して決める」（2026-07）と、独断せず相談に回している。
