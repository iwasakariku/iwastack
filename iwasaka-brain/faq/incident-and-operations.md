> [!summary] TL;DR
> 初動は「どの環境で・どのコミットが・初発か再発か」の事実確認。生ログを加工せず貼り、対症療法ではなく時系列の整合が取れる根本原因まで追う。
> 沈黙を成功と誤認しない。デプロイ完了は digest 一致、復旧は実体照合で確認する。本番操作と不可逆な操作は退避を先に取って自分の手で。
> 境界は既定で閉じ、例外はローカルだけ。「直す方が危ないバグは直さない」。

## 想定問答

**Q: 本番でエラーが出ている。どうする？**
A: まず対象環境に載っているコミットを確定し、「初めてか再発か」「すでに対応中か」「直前の変更と関係あるか」を事実で切る。ログは加工せず生のまま貼って一段ずつ絞る。場当たりの修正はせず、全体を見通して根本原因まで追う。→ [[iwasaka-brain/patterns/bug-triage-and-incident|障害・不具合対応の初動]]
根拠: 障害対応 93 セッションの初動が「貼る→初発か再発か→直前変更との関連を切る」の順で一定している。

**Q: 直前のデプロイが原因では？**
A: 決めつけない。「前は動いていたなら根本原因はそこじゃない」と時系列の整合を取る。原因が無関係なローカル設定・旧イメージの残存・WAF・無効な認証情報・別サーバーの起動だった例が多い。反映されないときはデプロイ手順より先に「本当に稼働しているコードか」を疑う。→ [[iwasaka-brain/principles/operability-and-observability|運用・監視・コスト]]
根拠: 「前は動いていたので根本原因はそこじゃない」で AI の誤った因果説明を 2 度退け（2026-07）、2026-09 に「稼働コードの実体確認」へ重心が移っている。

**Q: デプロイ完了しました。**
A: 稼働中の digest と push した digest が一致するまで完了とは言わない。現行イメージが想定タグ以外なら失敗させて、古いイメージのまま成功に見える状態を潰す。デプロイ経路ごとに何が配られるかを把握しておく。→ [[iwasaka-brain/principles/operability-and-observability|運用・監視・コスト]]
根拠: 「デプロイ完了は稼働中 digest と push した digest の一致で確認する」「想定タグ以外なら失敗させる」（2026-09）。

**Q: エラーログが出ていないので正常ですよね？**
A: 沈黙は成功ではない。エラーが出ない滞留は時間メトリクスで検知し、失敗シグネチャも監視する。「エラーが無い」と「試されていない」は別。ログ基盤自体は作業を止めない fail open で組む。→ [[iwasaka-brain/principles/operability-and-observability|運用・監視・コスト]]
根拠: 「沈黙を成功と誤認しない」（2026-06）、「エラーログが出ない滞留は時間メトリクスで検知する」（2026-07）。

**Q: 本番 DB を直接直していい？**
A: 本番操作は AI に代行させず自分でやる。調査は読み取り系に限り、調査目的でも本番環境には触らない方針。不可逆な操作はバックアップ・退避を先に取り、移行後も旧データは消さず残す。運用で使う SQL は内部 ID ではなく業務コードで対象を指定する。→ [[iwasaka-brain/principles/operability-and-observability|運用・監視・コスト]]
根拠: 「本番操作は AI に代行させず自分で実行し結果を貼る」（2026-08）、「データ移行は必ずバックアップを取ってから、旧データは消さない」（2026-08）。

**Q: 恒久対応まで時間がかかる。どうする？**
A: 暫定策（機能を閉じる等）を先に打ち、恒久対応は issue に残す。暫定回避と本筋修正は区別して扱う。dev 環境で自然収束する実害小の問題なら対策を見送って記録だけでいい。→ [[iwasaka-brain/principles/quality-vs-speed|品質と速度の置き方]]
根拠: 「恒久対応までの間は機能を閉じる暫定策を先に打つ」（2026-09）、「実害小の問題は対策を見送り記録だけ残す」（2026-07）。

**Q: 監査で指摘が N 件出た。全部直す？**
A: 「危険な行がある」と「その行に到達する」は別。誰がどの経路で踏めるか、直した後の攻撃面がどうなるかを実測で比べて優先順位を決める。実測されたバイパスは即修正、到達不能なものは背景として記録して終える。直す方が危ないバグは直さない。→ [[iwasaka-brain/principles/multi-tenant-safety|テナント境界と認可への姿勢]]
根拠: 2026-08 に「破られた先で何を失うかを実測して優先順位を決める」、2026-09 に「直す前に到達経路と修正後の攻撃面を比べる」「直す方が危ないバグは直さない」。

**Q: フロントで権限制御しているから大丈夫ですよね？**
A: フロントのガードは担保ではない。API 側の担保を確認する。権限系の確認は一般ロールで行う。最上位権限で試すと偽陰性になるので、テストユーザーのロールは画面要件から決める。性能改善のような無関係に見える変更でも境界の検証は省かない。→ [[iwasaka-brain/principles/multi-tenant-safety|テナント境界と認可への姿勢]]
根拠: 「フロントの UX ガードだけで安心せず API 側の担保を確認する」（2026-06）、「テストユーザーのロールは画面要件から決める」（2026-09）。

**Q: 便利なのでローカルの例外設定を本番にも入れたい。**
A: 入れない。境界は既定で閉じ、例外はローカルだけ。セキュリティの既定は厳しく保ち、利便性のための例外を本番側に持ち込まない。本番データへの書き込み経路は一切許容しない。認証が取れないときは fail-closed。→ [[iwasaka-brain/principles/multi-tenant-safety|テナント境界と認可への姿勢]]
根拠: 「他テナントのデータが見える可能性のある経路は既定で遮断し、ローカルのみ例外」「本番データへの書き込み経路は一切許容しない」（2026-07）。

**Q: 鍵が漏れたかもしれない。**
A: 失効・再発行する。旧キーは削除させず退避。公開・引き継ぎ・バックアップの前には秘密情報の混入を必ずスキャンし、鍵や接続設定は手動移行リストに分離する。認証情報はコードに書かず実行時に OS の資格情報ストアから読む。→ [[iwasaka-brain/patterns/security-mindset|セキュリティへの姿勢]]
根拠: 「流出の疑いがある鍵は失効・再発行する」（2026-08）、「公開前・引き継ぎ前に秘密情報の混入を確認する」（2026-10）。

**Q: この対策、コストはどのくらい？**
A: 体感ではなく実測と公式料金で出す。ログの実測値から計算し、料金ページは自分で確認する。0 円に見える案でも設計変更コストを見落とさない。開発環境のコストは速度の後ろに置いていい。→ [[iwasaka-brain/principles/operability-and-observability|運用・監視・コスト]]
根拠: 「コストはログの実測値から計算する」（2026-07）、「コスト試算は公式料金ページを自分で確認して数字を出す」（2026-08）。

**Q: 障害が収まった。次は何をする？**
A: 根本がデプロイ漏れなど運用にあるなら仕組みで防ぐ。無言死の構造には fail-fast / fail-closed を入れ、裏に同種の反映漏れが無いかを横展開で確認し、手順書に反映して恒久化する。レポートは「落ち着いた、レポートをまず」でファイル変更なしから始める。→ [[iwasaka-brain/patterns/bug-triage-and-incident|障害・不具合対応の初動]]
根拠: 「障害の根本が運用にあるなら仕組みで防ぐ」（2026-07）、「設定・権限の確認から入り同種の反映漏れを横展開で確認する」（2026-08）。

## 本人が答えに迷う・保留する問い

- **fail-closed かフォールバックか。** 「認証が取れないときは fail-closed」（2026-09-18）と「権限不足時は失敗させず安全に従来方式へ戻す」（2026-09-28）が併存する。認証そのものは閉じ、追加機能の権限不足は従来方式が安全と確認できる場合だけ戻す、と読めるが基準は明文化されていない。
- **監査指摘をどこまで受容するか。** 「構造的に不可避なら根拠付きで受容」「未知の利用者がいる経路は塞がず再発防止のコメントを残す」（2026-07）と、塞ぐことで業務を止めるリスクも天秤にかけており、即答せず運用前提と照らして決めている。
- **運用の手当てを SQL でやるか画面機能にするか。** 「機能が無いなら当面は SQL で手当てし恒久対応は issue に残す」と「運用で API を直接叩く回避策は取らず画面機能として実装する」（2026-09）が併存し、どこまでを暫定で許すかは案件ごと。
