> [!summary] TL;DR
> 設計の既定は「既存の同型に揃える・正本は 1 箇所・契約は不変・分割は認知負荷が下がる分だけ」。
> 技術選定は「今ぶつかっている制約で選ぶ」。理由と撤退条件を先に書き、全面採用より必要な箇所だけ準拠する。
> 決めきれない論点は実装から切り離し、実測・実コードで決着させる。

## 想定問答

**Q: 新機能、どこから設計を始める？**
A: まず既存の同型パターンを探す。既存画面・既存規約・直近の完成形に揃えるのが正解形で、新しい構造を持ち込むのは既存で足りないと分かってから。新規開発の前に「既存の仕組みで足りるか」を確認して、作業量が桁違いに変わる分岐を先に潰したい。→ [[iwasaka-brain/principles/simplicity-and-reuse|シンプルさと既存の踏襲]]
根拠: 2026-06 に UI の挙動・操作モデル・規約を既存ページの同型に合わせる判断が約 20 件、2026-09 に「新規開発の前に既存で足りるか確認」が繰り返されている。

**Q: このモジュール、分割した方がよくない？**
A: 分割は認知負荷が下がる分だけ入れる。150 行程度なら 1 ファイルで、足すなら一層程度。分割のための分割は回帰リスクの方が高いのでやらない。複雑に感じたら、既存概念に引っ張られていないかを先に疑う。→ [[iwasaka-brain/principles/simplicity-and-reuse|シンプルさと既存の踏襲]]
根拠: 「規模に見合わない過剰分割は避ける（150 行程度なら 1 ファイル）」（2026-06）と「分割のための分割は回帰リスクの方が高い」（2026-09）が併せて観測されている。

**Q: リファクタで controller や層構造を分けたい。**
A: 契約は破らない。生成コードや API が依存する名前は不変が条件で、構造移動と挙動変更は同じ PR に混ぜない。順序は「減らす（削除・SSOT 化）」を「動かす（移動・分割）」より先に。契約不変かつゲート全緑なら PR まで止めずに流して OK。→ [[iwasaka-brain/patterns/refactoring-approach|リファクタ・整理のスコープの切り方]]
根拠: フロント生成コードが controller クラス名に依存するため分割を契約破壊と判定し、「モジュール集約・契約完全不変」の案を選んだ（2026-06）。

**Q: 同じ列挙値や定数が複数箇所にある。どうする？**
A: SSOT を 1 箇所に置いて各層が参照する形にする。ただし「似て非なる集合」は 1 つに潰さず別定数として契約を守る。揃えるべき値の食い違いはテストで検出する。→ [[iwasaka-brain/principles/type-safety-and-static-guards|仕組みで守る]]
根拠: 2026-06 に列挙値の SSOT 化と「似て非なる集合は別定数」の判断、2026-09 に「同じ語句の重複定義は 1 箇所管理にし食い違いはテストで検出」が観測されている。

**Q: 新しいライブラリやツールを入れたい。**
A: 今ぶつかっている制約で選ぶ。導入前に「それが本当に課題を解くか」を確認し、解かないなら入れない。上流や方法論は丸ごと取り込まず、必要な箇所だけ準拠する。新規ライブラリなら可否調査のうえ、開発ルールへの組み込みまでセットで。→ [[iwasaka-brain/patterns/migration-and-tool-evaluation|乗り換え調査・ツール比較の型]]
根拠: 既存ツールと代替の比較で「今ぶつかっている制約で選ぶ」と既存継続を決め（2026-06）、上流 24 コミットの取り込みを「丸ごと更新はオーバースペック」と反転した（2026-08）。

**Q: ランタイムやメジャーバージョンの乗り換え、やる？**
A: 理由と撤退条件を先に書く。「とんでもないことになるなら後回し」を宣言してから、実装はせず調査だけで段階的に選択肢を絞る。既存テストを新版で実際に回して判断し、公式情報とサンプルが食い違えば公式を正とする。→ [[iwasaka-brain/patterns/migration-and-tool-evaluation|乗り換え調査・ツール比較の型]]
根拠: 2026-09 に API 可用性・拡張・テスト環境・ビルド可否の 4 系統を並列実測し、「PoC 中に移行コストを下げたい」と撤退条件を先に置いた。

**Q: 権限で見せ分ける情報、どう設計する？**
A: DTO の型として分離し、必須化で相互代入を止める。フロントのガードは担保にならないので API 側で担保する。一般ユーザーにも返る応答には運用情報を足さず、専用 API に理由付きで足す。→ [[iwasaka-brain/principles/multi-tenant-safety|テナント境界と認可への姿勢]]
根拠: 2026-09 に「権限で見せ分ける情報は DTO の型として分離」「運用者の作業量は特権者だけに表示」の判断が観測されている。

**Q: 将来のために汎用的に作っておいた方がよくない？**
A: 体感価値の大半が得られるなら削る。思いついた機能追加は理由を聞いて、不要なら捨てる。サービスイン当初は人が介在する前提で機能を減らしていい。ただし既に存在していて再利用が具体的に見えるもの（表示切替フラグ等）は残す。→ [[iwasaka-brain/principles/simplicity-and-reuse|シンプルさと既存の踏襲]]
根拠: 「体感価値の大半が得られるなら自前実装は削る」（2026-06）と「仕組みは将来の段階公開にも使えるので残す」（2026-09）が併存している。

**Q: 設計で意見が割れた。どう決める？**
A: 実クエリ・実コードで決着させる。もっともらしい分析より実測。それでも決まらない論点は実装から切り離し、「決めること」を先頭に置いた短い issue にする。案を採用するときは不採用案と理由も残す。→ [[iwasaka-brain/principles/decision-under-uncertainty|不確実な中での決め方]]
根拠: 「設計議論の主張は実クエリで決着させる」（2026-07）、「方針未決の論点は実装から切り離し短い issue にする」（2026-09）。

**Q: 汎用 BI や LLM 連携を自前で持つべき？**
A: 持たない。汎用 BI は内蔵せず探索は LLM/MCP に任せる。LLM の起動・課金・会話はホスト側に任せ、自前で抱えない。1 ボタン用途なら、アプリ登録や署名検証が増える方式より軽い構成を選ぶ。→ [[iwasaka-brain/principles/simplicity-and-reuse|シンプルさと既存の踏襲]]
根拠: 2026-09 に「汎用 BI は内蔵しない」「LLM の起動・課金・会話はホスト側」「1 ボタン用途なら軽い構成」の 3 判断が観測されている。

**Q: 認証は全社統一の IdP に寄せる？**
A: 外部企業の利用を前提にするなら採らない。先に決めるのは認証の責任の置き場で、自社が預かる資格情報なのか、顧客組織が発行する身分なのか。人の台帳・認証・利用権は層を分けて考える。→ [[iwasaka-brain/principles/multi-tenant-safety|テナント境界と認可への姿勢]]
根拠: 2026-09 に「外部企業の利用を前提に全社統一 IdP は採らない」と、台帳・認証・利用権の 3 層分けを受け入れた判断がある。

**Q: 本番前の最後のリファクタ。安全寄りで小さく？**
A: 逆。触るなら本番稼働前の今しかないので、安全寄りではなく思い切った Tidy First で行く。ただし 1 PR は小さく、フェーズ別に前 PR マージ後にベースから切る。「分けすぎは本末転倒」の上限は同時に置く。→ [[iwasaka-brain/patterns/refactoring-approach|リファクタ・整理のスコープの切り方]]
根拠: 2026-06 に「本番稼働前の最後の機会として思い切った Tidy First」と「分けすぎは本末転倒、一層足す程度」を同じ時期に指示している。

## 本人が答えに迷う・保留する問い

- **共通化をどこまで広げるか。** 部品単位は揃えるが、エンティティ編集フォーム単位では無理に揃えない。横展開が大きくなるときは「修正量より一貫性を優先するかは相談して決める」と独断せず相談に回す（2026-07, 2026-09）。
- **設計の前提が崩れたときに作り直すか。** 前提はコードで反証してから動くのが基本だが、崩れていても本人判断で設計どおり進めた例がある（2026-08）。保留が常に正解ではなく、決めた以上は決めた側に倒す場面がある。
- **残すか削るか（YAGNI の境界）。** 「価値の大半を得たら止める」と「再利用が具体的に見えるものは残す」が併存し、境界は案件ごとの判断になっている。
