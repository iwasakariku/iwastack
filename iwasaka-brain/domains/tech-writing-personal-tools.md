## この領域での典型的な進め方（型）

1. **記事化**（09-15、09-16 の 2 セッション）: ソース全文や定義・フック実装・実走報告を順に貼り込む→「解説を〜記事にして」→草稿に敵対的レビュー→指摘を一つずつ妥当性判定→IDE で確認→「OK 投稿して」。執筆はサブエージェント 1 体に委譲し、投稿は CLI。本人は素材提供と採否判断に徹する。
2. **翻訳**（08-07〜08-08 の 8 セッション）: 「日本語にしたい」と一言で始め、AI が出す選択肢に番号・記号で答えて範囲を絞る。自分が使う範囲（Claude Code 向け＋共通）だけに縮小し、使わない章は原文へのリンクで逃がす。完成後は「簡易的で OK なので、敵対的にレビューして」。行範囲指定の翻訳は「日本語にして @〈ファイル〉(行範囲)」。
3. **個人ツール**（06-24、08-07）: センサー条件・温度条件のように 1 文で指定して実装を一任。デバッグ出力や DOM ダンプをそのまま貼り、算出結果は自分で検算して「2 重になってそう」と指摘、「良さげ」で確定。
4. **トラブルシュート**（06-25、08-26）: クラッシュログ全文を貼った一問、または実測値（800KB は OK、1.4MB はエラー）を添えて「〜って上限あったりしますか？」→原因説明→「〜ジャストの〜を作って」で検証素材を要求。
5. **1 往復で済ませる定型作業**: PR の URL だけ渡してコミットメッセージ、例を 1 つ示してサブモジュール一括クローン。

## この領域固有の判断基準・注意点

- **実際に試していないことは記事に書かず、「試していない代替案」として明示する**（09-16）。
- **「物理的に守る」のような強い表現は実測の範囲までトーンダウンし、差別化や ROI の未計測は数字を作らずそのまま書く**（09-16）。
- **自作ツールの解説は設計方針と変更履歴を含めて公開する**（09-15）。
- **成果物は完成宣言の前に敵対的レビューにかける**（2 回: 08-07 翻訳、09-16 記事）。AI 自身の成果物を否決前提で見させ、見出し数の一致だけで翻訳完了と判断しない。
- **翻訳は原文を残して併置する**（upstream 貢献を妨げない）。自分が使わない範囲は翻訳せず原文へリンク（08-07）。
- **コミットメッセージはリポジトリの既存規約に合わせる**（06-22）。
- **算出結果は自分で検算し、画面構造の推測より実 DOM のダンプを根拠にする**（08-07）。
- **上限の仮説は境界値ファイルで実測して確定する**（06-25）。
- **機密情報はバックアップに含めず手動移行対象として別リストにする。不要な作業（Git 未プッシュ確認）は早めに止める**（10-05）。
- **関連リポジトリ群は親リポジトリで俯瞰できる状態にする**（07-26）。
- 設定ファイルの所在は AI に探させ、返ってきたパスをそのまま vi で開く（06-17、単発）。
