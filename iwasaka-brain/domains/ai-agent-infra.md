## この領域での典型的な進め方（型）

1. **スキル作りの流れ**（07-07、07-17、07-22 の 3 セッション）: 既存試作の成功例・失敗例で課題を言語化（「公式ドキュメント偏重で AI に聞いた意味がない」）→設計検討→実装→サブエージェントで典型・ニッチ・境界・曖昧入力・セキュリティ・キャッシュのテストケースを並列実行→改善候補を抽出→コミット／draft PR。生成はサブエージェントに任せ、主エージェントが仕様チェックリストで検収する。
2. **ゴール指定で丸投げし、進行を短く承認する**（07-05 ×2、08-20）。「〜を完璧にして」「レベルアップして」と抽象的に委ね、AI の多角設計→敵対的レビュー→再検証の進行を「続けて」「お願いします」「全部実行して」で承認。読み取り専用の監査→承認→実行の順を守り、長引くバックグラウンドエージェントは停止して「続けて」。
3. **拡張開発は UI 仕様を表示文字列レベルまで具体化**（06-17、09-07）。表示形式の文字列例・ホバー内容・消費ペースの可視化を明示し、スタックトレースを貼って修正を反復、「これは関係ないエラー？」と切り分けを問う。「可能？」で始めて「進めて」で委譲し、提示案を採用しつつ既定値を自分で指定する。
4. **実装はサブエージェントに委譲し、司令塔（本体）が自分で再実行して検収**（09-07、09-09）。本体では実 API のプローブとパッケージングを並行させる。
5. **一言確認**: 「〜に使えるスキルはある？」「〜のバージョンや実行情報を教えて」「グローバルの〜の〜を〜にしたい」。

## この領域固有の判断基準・注意点

- **スキルはリポジトリ作業ツリーから切り離した固定コピーで配置し、更新時は再コピーで上書き**（06-15）。
- **特定プロジェクト固有の名称・パスは除去し、実行時に対象リポジトリの規約を読む形に汎用化する**（07-17）。
- **ソースカタログは実際の共有実績から作る**（07-22）。
- **スキルはテストケースで検収してからコミットする**（2 回: 07-07、07-22）。作ったスキルはすぐ実テーマで試し、レビュー前は draft で PR を出す。
- **実測で踏んだ制約（サブエージェントのタイムアウト）はスキル文書に残す**（07-07）。
- **まとめられるものは 1 PR にし、横展開の残りを自分から確認する**（「まだやること残ってる？」07-07）。
- **破壊的操作（マスキング・改名）は自分の手で実行し、削除ではなく可逆退避にする**（07-05）。**権限で止まったコマンドも自分で実行する**（09-09）。合わせて 2 回。
- **監査成果物はローカルに留め、リモートへはスキル修正のみ出す**（06-10）。
- **公開前に秘密情報の混入を確認する**。認証情報はコードに書かず実行時に OS の資格情報ストアから読む（10-06）。
- **API が 200 を返すなら壊れているのはクライアント側と切り分ける**（09-09）。
- **枠が増えても描画側を変えない汎用構造にする**。ツールチップの巻き戻り・幅ズレといった体感レベルの不具合も放置しない（09-07）。
- **完了条件を観測可能な形（ログイン画面が開く）で定め、掃除系操作の影響範囲を確認する**（「消してないよね？」08-20）。既存 PR に積む。
- **メモリ暴走の予防策はセッション分割・MCP 削減**（07-02）。トークンが無駄になった時は率直に返金を要求する。
- **司令塔モデルの effort は medium**（07-16、単発）。
