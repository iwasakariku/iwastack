> [!summary] TL;DR
> 主戦場は Claude Code（504 件）。Cursor（358 件）は 6 月前半の監査サイクルと 9 月中旬の短い確認・理解の対話に集中し、7〜8 月はほぼ使っていない。
> 基本形は「司令塔 1 体＋役割別サブエージェント（偵察・フェーズ別実装・独立レビュー・反証・認可監査・契約チェック）＋固定の出荷ゲート」。Agent を使ったセッションは 193 件（38%）、9 月は半数、1 セッション最大 34 体。
> 自分で握るのは計画承認・実機スモーク・マージ・判断の記録。AI の完了報告は実測で裏取りし、誤りを訂正した記録が 30 件超ある。

## Claude Code と Cursor の使い分け

| | Claude Code | Cursor |
|---|---|---|
| 件数 | 504（6 月 111 / 7 月 144 / 8 月 99 / 9 月 135 / 10 月 15） | 358（6 月 211 / 7 月 6 / 8 月 31 / 9 月 110） |
| 1 件の重さ | ユーザー発話の中央値 5、平均 8.3、最大 118 ターン | 1 依頼 1 ブロック。「コミット」「計画 OK」の一語も 1 件 |
| 時間帯 | 10〜11 時に偏る（46・85 件） | 16〜18 時に偏る（53・66・33 件） |
| 向いている仕事 | チケット 1 件のフルサイクル、全域監査、長時間の実装・レビューループ | エディタ内の短い確認、仕様の所在確認、SQL 生成、理解のための往復 |

Cursor の 358 件は 3 つの塊でほぼ説明できる。6/8〜6/10 の 211 件は自作の Web 監査スキルを Cursor エージェントで回した監査サイクルで、「検査→壁打ち→計画→人間ゲート→実装→他 AI レビュー→スモーク→PR」を 1 機能ずつ細切れに進めた。9/16〜9/18 の 97 件は DuckDB 版数統一の残課題、検証環境デプロイの権限エラー、本番 WAF 403 の切り分け、セキュリティ 2 課題を腹落ちするまで問い直す 20 問超の対話。7/28 の 6 件は別の AI が出した MCP 遅延分析の妥当性を検証させる用途。**短い問いを矢継ぎ早に投げ、表で整理させ、理解が合っているかを確認する**のが Cursor での使い方で、実装の主体は 6 月中旬以降 Claude Code に移った。

Claude Code 側はツール集計がそのまま働き方を表している。Bash 23,385 回に対し Edit 5,802・Read 3,738 で、司令塔はコードを読むより検証コマンドを回す。AskUserQuestion 584 回（182 セッション）は AI 側からの選択式質問に番号で答える運用で、7/17 の設計ステージでは 29 回、9/7 のトライアル設計では 16 回答えている。9 月は Edit 35・Read 31 セッションに対し Agent 67・Skill 47 と、**司令塔自身が編集・読解をほぼしなくなり、委任と検収に専念する**形に収束した。

## サブエージェントの使い方

Agent を使ったセッションは 6 月 35 / 7 月 44 / 8 月 41 / 9 月 67 / 10 月 6。1 セッションあたりの投入数は 6 月平均 3.8 体 → 8 月 7.0 体で、10 体以上を使ったセッションが 19 件、最大は 7/17 の合成データウィザード全フェーズ実装（34 体）、8/25 のプラン管理・請求（31 体）、9/28 の引き継ぎボード（26 体）。

役割は観測上、次のように固定化している。

- **偵察・調査**: Explore を複数角度で並列し、読み取り専用で網羅調査（6/25 列挙値マッピング、7/12 WMS 連携先、9/18 要望の深掘りに 5 体）。
- **フェーズ別実装（GREEN）**: 計画書のフェーズごとに 1 体、worktree で並走（9/2 で 3 worktree×3 体、9/23 で 5 体）。
- **RED 専任**: 製品コードを書き換えずに失敗するテストだけを書く敵対的テスター（9/16 新設、4 体並列で RED 11 件）。RED と GREEN を別エージェントに分ける（9/11）。
- **独立レビュー 2〜3 巡**: 正しさ・セキュリティ・API 契約・脆弱性のレンズ別に並列し、修正が尽きるまで巡回（8/25〜27 で 3 ラウンド、9/10 以降は標準 2 巡）。
- **反証専任**: 成果物の主張を壊しにいくサブエージェントをグローバルに追加（8/6）。計画書の前提を実測で崩す用途（8/6 で CI が起動しない致命的前提を発見、8/21 で期待効果の誤読を発見）。
- **認可・テナント分離監査、契約チェーン検証、割り込み影響分析、ゲート再実行**: 9 月の請求系フルサイクルで毎回ついてくる定番セット。

司令塔の検収は「diff 直読＋ゲート再実行」で、サブエージェントの報告を信用しない。AI 自身が前セッションの「検証済み」主張を再突合して誤記を直した例（7/13）、サブエージェント 2 体の報告を鵜呑みにせず司令塔がコードを精読した例（6/17）、改善主張 3 件が誤差と判明して撤回させた例（8/3）が記録され、**「実測という語が実測の中身を保証しない」**という学び（8/6）に集約されている。

モデルの使い分けは、実装は軽いモデル・レビューは上位モデル（7/17）、最終レビューに別モデル（9/28）という方向で試しつつ、9/18 には高コストモデルの使用停止→全サブエージェントを inherit に統一→ルール変更を撤回、と揺れた。

## スキル・ワークフロー・フック

Skill は 174 回・130 セッションで使われ、大半が自作。時系列で積み上がったものは次のとおり。

- 6/8 Web 監査スキル（約 1,700 行、8 ステージ）／6/15 バグ修正フルサイクルスキルと再発パターンのカタログ／6/25 出荷ゲートスキル（型チェック→テスト→lint→swagger 差分→DI 起動スモーク→PR）。
- 7/7 データ基盤 MCP で物流の問いに答えるスキル 6 本／7/9 スプリントレビュー生成スキル／7/13 WMS スキーマ辞書スキル（5 ドメイン 50 超テーブル）／7/22 多視点調査スキル／7/17 スキルに TDD の RED 観測ゲートを追記。
- 8 月〜 起票スキル、計画書テンプレート（8/17、AI-DLC v2 の 3 概念のみ採用）／9 月 issue フルサイクル（偵察→質問ファイル→RED→GREEN→独立レビュー→スモーク→Done コメント）。

ワークフロー型の多観点レビュー＋反証検証は 6〜7 月に多く（13・11 件）、7/10〜7/12 の全域監査では 176 バッチの発見→反証検証を並列化し、未検証をモデル分散で潰し切った。8 月以降はワークフローよりサブエージェント直叩きに置き換わる。

フックは「ゴール駆動」に使う。Stop フックで完了条件を満たすまで止まらせる運用が 7/10 の全域監査、8/18 のローカル AWS エミュレータの代替調査、8/20 のセットアップ集約、10/5 の 2 日間移植セッション（118 ターン、サブエージェント 19 体）で観測される。PostToolUse で編集ごとに型チェックを走らせる試みは拒否されて未適用（6/25）。外部フレームワーク（AI 開発ライフサイクル）は 8/6〜8/10 に深夜まで試走し、「ホストをスタブしたテストでは手写しの契約を誰も検証していない」構造を見つけたうえで、テンプレに 3 概念だけ取り込んで本体は採用しなかった。

## MCP

MCP は「使う」と「作る・測る」の両面にある。使う側では、自社データ基盤の MCP サーバーで SQL を実行（SQL 実行ツール約 170 回。6/29 の顧客分析では 30 回超を回して HTML レポート 2 本）、課題管理 MCP が 8 月から急増し作成・取得・コメント約 980 回で判断を全部チケットに残す運用に変わった。ほかに Obsidian（知見ノートの保存）、Slack（文面と検索）、Google Drive（資料の読み込み）、デザイン同期ツール（8/12 にモックを 31 回反復）。作る側では、自社 MCP の初回応答 8 秒を k6 の対照実験で microVM 起動費と確定し（7/28）、商談で遅い原因が往復回数だと監査ログで実測し（8/21）、外部 AI クライアントからの接続要件を 25 回の Web 検索で洗い出した（9/2、9/30）。

## 自分で持つ仕事と任せる仕事

| 自分で持つ | AI に任せる |
|---|---|
| 計画承認、スコープの境界（やる・見送り・後回し） | 計画書の起草、前提の実コード突合 |
| 実機スモーク（想定ロールのユーザーで） | 実装、テスト、ゲート実行、コミット、PR 本文 |
| push・マージ・デプロイ・DB 直接操作・認証ログイン | コミットメッセージ、ブランチ運用、worktree 管理 |
| 本番からのログ・slowlog 収集、ブラウザでの観測 | ログの解析、仮説の更新、コード照合 |
| UX の判断（表示秒数、UI モデル、文言の採否） | UI 実装、文言案の列挙 |
| 他 AI・サブエージェントの指摘の採否、レビュー判定の最終決定 | レビューそのもの、反証、変異テスト |
| 関係者への確認・送信（Slack は自分で送る） | 文面の起草、Linear コメントの下書き |
| 判断の記録先と記録形式の決定 | 記録の作成（クローズ記録 4 項目、採らなかった案と理由） |

線引きの原則は「不可逆な操作と、外に出るものは自分」「読む・書く・検証するは AI」。6/23 に「契約不変かつゲート全緑の構造移動は PR 作成まで確認なしで進める」と決めて以降、人間ゲートは振る舞いが変わる変更の手前に絞られている。

## 6 月 → 10 月の変化

| 時期 | 使い方の重心 | 象徴的な出来事 |
|---|---|---|
| 6 月前半 | Cursor でスキルを回し、別 AI にレビューを手動リレー（他 AI レビュー 16 件、6 月のみ） | 「壁打ち文章を作って」→別 AI→結果を戻す |
| 6 月中旬〜下旬 | Claude Code へ移行、フルサイクルスキルと出荷ゲートの固定化、worktree 並走 | 契約不変なら PR まで無人、人間は計画承認とスモーク |
| 7 月 | ワークフロー型の全域監査、goal プロンプト＋Stop フック、司令塔とサブエージェントの役割分担をルール化（7/15） | 176 バッチの発見→反証→モデル分散で検証完了 |
| 8 月 | 反証専任サブエージェント、敵対的レビュー 3 ラウンド、Linear MCP で判断を全部記録、外部フレームワークの試走と取捨 | 「実測という語が実測を保証しない」 |
| 9 月 | issue フルサイクルの定型化（偵察→RED→GREEN→レビュー 2 巡→Done）、変異テストで検出力を担保（14 件、9 月から）、敵対的テスターの新設と記事化 | 1 チケット 1 セッションで Done まで |
| 10 月 | ゴール駆動フックで 2 日間止めずに移植、引き継ぎ用のチケット補足 | 118 ターン・約 40 万字の最長セッション |

通底する変化は、**「AI にやらせる」から「AI に壊させてから信じる」へ**。6 月は他 AI のセカンドオピニオンを人手でリレーしていたが、8 月には反証専任エージェントが常設され、9 月には変異テストと RED 専任テスターで「テストが本当に落ちるか」まで機械的に確かめるようになった。もう一つは記録の置き場で、6 月はリポジトリ内の計画書・トラッカー、7 月はメモリと Obsidian、8 月以降は課題管理ツールのコメントに判断・採らなかった案・未決事項を残す形に一本化された。
