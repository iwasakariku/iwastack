> [!summary] TL;DR
> チケット番号だけで着手し、起票は「既存確認→プラン→起票案で停止→承認後作成」。見積は計画確定まで空欄。
> コミット・push・PR・マージはすべて明示指示。squash は使わず merge commit、PR は 1 つずつマージしてから次。
> 同じ原因・同じ方式で直せるものは同じ PR、再考が要るものだけ別イシュー。

## いつ発動するか

ほぼ全ての実装セッション。6 月は Cursor の定型コマンドでコミット文生成、7 月から課題管理ツールの MCP 連携、8 月から起票スキル、9 月からチケット駆動のフルサイクルスキルが中心。

## チケット側の流れ

1. **番号だけで開始。** 「チケット番号で直して」「〜の課題を続行して」「状況って？」。AI が課題管理と実コードの双方で状態を突合する。
2. **起票は承認後。** 起票スキルの手順は既存確認→プラン→起票案で停止→承認後作成。「一旦起票して」「起票 OK」「投稿 OK」。書き込みは指示待ち、「課題管理は更新しないで」の制約もある。
3. **重複を疑う。** 「別チケットとの違いが分かりにくい、既存の範疇では」と新規起票を却下し既存へのコメント反映を選ぶ（8 月）。「似たチケットの重複を疑った」「全件が起票済みかを突合」。
4. **分割か同梱か。** 同じ原因で直せるもの・スモークで見つけた画面不具合・レビューで出たスコープ外のセキュリティ改善は同じ PR に（「ここで対応して」）。重要で再考が必要なものは「別イシューで再考」「別イシューでトリアージにして、デイリーで簡潔に方針をまとめられるように」。「別イシューは切らず、このブランチで全て対応」も明示する。
5. **見積。** 計画確定まで空欄。「1 ポイントで十分」「1 ポイントぐらいじゃない？多すぎない？」。他リポジトリの運用を貼って SP 計算を最適化。
6. **紐付けを直す。** 「親チケットで PR はわかりにくいので子チケットを作って載せ替えて」。親子・related の整理、1 件を親から外す自己訂正を受け入れる。
7. **Done 化。** 「マージした」→Done とクローズ記録コメント。「デプロイ手順は不要」と不要出力を切る。ステータス変更は依頼範囲外なら触らせない。親チケットの完了条件は実態に合わせて読み替える。

## PR・ブランチ側の流れ

- **常に明示。** コミットは「コミットして」、push は「push して」「pushはしないで」、PR は「PR して」。6 月から一貫して AI に勝手に push させない。「push → 自分でマージ」を選ぶこともある。
- **ベースの実確認。** 規約ファイルより実マージ履歴を優先してベースを判断させる。「main から切らない」ガード、「スプリント統合ブランチベースで」、「〜マージ後の状態で進めたい」「プルしたので最新で進めて、重ならないなら OK」。前 PR マージ後にベースから切る（スタックしない）。
- **ブランチ戦略の相談。** 「今のブランチがそのまま統合ブランチに入る前提で可能か」→正式手順とスタックブランチの 2 案比較（6 月）。「〜みたいな感じでさらにブランチ切って、feature を切って」。
- **worktree で並行。** 「別件コーディング中なので他ワークツリーで」「ブランチ切り替えはワークツリーで別のところで」。cherry-pick 用の一時 worktree で IDE の編集と干渉させない。
- **PR の粒度。** 「3 チケットを束ねて 1 PR」「A→B→C→D の順で 1 つの PR に最終的にまとめて」「swagger の再生成は別コミットで」「PR テンプレのみ main 向け、他はスプリント向け」と分割。docs 専用 PR は統合ブランチ基点に cherry-pick し直す。
- **チケットキー。** 捏造しない。キーなしで PR を進めてよいかは AI が確認、docs 変更はキー不要の運用を実 PR から確認させる。
- **CI。** バックグラウンドで完走を待たせる。CI の既存失敗（lint 設定・無関係テスト）は本変更と切り分けて報告させる。rebase 後はゲートを再実行。
- **マージ方式。** squash は履歴が消えるので使わない（過去の squash-merge が履歴構造の原因と判明、8 月）。merge commit 必須。PR を 1 つずつマージしてから次へ。

## 典型例

- **6 月・データ基盤**: 定型コマンドで差分を BE/FE/生成物に分類させ、BE と FE を別コミットに分ける方針で再実行。別件では細かい修正コミットを本来の変更単位にまとめさせた。
- **7 月・データ基盤**: 「PR 作成時はネクストステップまで進めて。今後も同様なので手順書に反映して」と運用をスキル側へ書き込ませた。
- **9 月・データ基盤**: 「〜の続き」で再開し、worktree 4 本で修正を並列委譲。終了時に push・PR・チケット更新・worktree 掃除は承認事項として残させた。

## 落とし穴・避けていること

- AI が PR に別件のワークアラウンドを混ぜないよう除外させる。gitignore の不備（個人設定や実行時ファイル）は AI の指摘を受けて対処。
- 公開前に秘密情報スキャン。「audit は push しないで」と範囲を限定して reset。
- 曖昧な指示の解釈（「未決事項は反映せず削除 OK」→別 issue は起票しない）を AI に明示させる。
- マージ状況は「コード側（merge-base）」と「課題管理側」の二軸で突合させる。

## 観測頻度

PR・コミット指示は約 150 セッションで全期間一定。チケット駆動は 8 月から急増（起票スキルの導入）し 9 月に最多。
