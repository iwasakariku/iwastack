> [!summary] TL;DR
> 初動はエラー全文かログをそのまま貼り、「初めてか再発か」「すでに対応中か」「誰の修正が原因か」の事実確認から入る。
> 一次証拠は自分で取り、AI は解読と仮説更新に使う。対症療法で済ませず、時系列の整合が取れる根本原因まで追う。
> 復旧操作は退避を先に、本番・push・マージの最終操作は自分の手で。

## いつ発動するか

ビルド・起動・ログインの失敗、CI の赤、デプロイ後のエラー、利用者からの問い合わせ、スモークで見つかった不具合。本番の遅延やデッドロック疑い（6 月、WMS）から、ローカル環境の設定ずれ（9 月）まで同じ型で動く。

## 初動（観測された順）

1. **貼る。** エラーメッセージ・スタックトレース・ターミナルログの行範囲・ブラウザのコンソール・CI のリンク。添えるのは一言の状況（「ダメそう」「変わらずエラー」「今度はこのエラー」）か仮説（「Docker のリセットが必要か」「ローカル DB をリセットしたせい？」）。
2. **事実確認を先に。** 「今までもあったのか初めてか調査して」「すでに対応が進んでいないか当日の該当時間帯のログを確認」「誰の何の修正がメインか」「誰のせい？治さなくて OK」（帰責の切り分けのみを依頼）。
3. **直前の変更との関連を切る。** 「本改修が影響？」「これは関係ないエラー？」。原因が UI 修正と無関係なローカル設定、ブラウザ拡張、旧イメージの残存、WAF、無効な認証情報、別リポジトリのサーバー起動と判明する事例が多い。
4. **一次証拠は自分で取る。** 本番では nginx エラーログ→アクセスログ→InnoDB モニタ、翌日はデッドロック→スロークエリ→FPM slowlog→EXPLAIN を順に貼り、AI は解読役（6 月、WMS）。AWS 側ではコマンド出力（スタック状態・関数更新時刻・イメージ digest）を逐次貼って照合させる（8 月）。
5. **再現条件を具体化する。** 「リロード後 1 回目は閉じる」「直線的に動かすと消える」「権限条件を変えたら再現した」。「ローカルで再起動しても再現しない、なぜ？」と差分の理由を追及する。

## 原因の追い方

- 「場当たり的に対応せず、全体を見通して対応して」（6 月）。「対症療法になっていないか、影響範囲や再発防止策も」（9 月）。
- 時系列の整合を要求する。「前は動いていたので根本原因はそこじゃない」「なんでエラーが出るようになったの？」で誤った因果説明を 2 度退けた（7 月）。
- 自分で反証実験する。「同名を削除しても同じことが起きる」「ハードリロードもした」「旧エミュレータを起動すると動くので向き先の変化かも」。
- 仮説を列挙して投げる。「シーダーかマイグレーションか env か調査して」「warn があるなら欠測日ゲート、無ければバッチ未起動」。
- ライブラリの仕様レベルまで掘らせる（Radix Dialog のモーダル仕様、React の参照同一性、DuckDB 拡張の HTTP タイムアウト既定値）。

## 復旧・判断

- **退避を先に。** 「バックアップとって実行して」。旧キーは削除させない（8 月）。「安全に戻せる？」と読み取り専用で reflog・ブランチ保護・オープン PR を確認させる（7 月）。
- **最終操作は自分。** push・本番マージ・デプロイ・権限で止まった削除は自分の手で。「push して自分でマージ」。本番の差分取得は途中で止めさせる。
- **実害で判断。** 実害小なら対策見送り・記録のみ（7 月）。恒久対応は「削除して、実装はいいや」で見送り、動くことを優先（8 月）。
- **運用改善に転換。** 旧イメージ残存が原因なら「デプロイ履歴の管理をしたい、何が最速？」。無言死の構造が分かれば fail-fast や fail-closed を入れる。
- **同じ原因は同じ PR。** スモークで見つけた画面不具合 2 件を同じ PR に含める。関連する別チケットも同じ方式で解決できるなら同時に（10 月）。
- **作業タイミングの確認。** 「今デプロイ中なんだけどその作業して良い？待った方が良い？」。

## 典型例

- **6 月・データ基盤**: ポップオーバーが閉じない不具合で、AI に計測用ログを仕込ませ、操作回数とコンソール出力を淡々と 4 回貼り続けた。4 回目で UI ライブラリのモーダル仕様が根本原因と判明。
- **7 月・データ基盤**: 「フラグ選択のやつが消えてそう」という体感を伝え、AI が履歴にないと言っても「絶対あったはず、統合ブランチにマージされていないかも」と別経路を探させ、復活後に「どこにあった？」と素性を確定させた。
- **8 月・データ基盤**: 失敗ログに対する AI の「ツールのバージョン起因」診断に「経路はずっとあった、env か何か足りないのかも、0 から作れば生きてるかも」と対案を出し、使い捨て環境での実証から再構築で復旧した。

## 落とし穴・避けていること

- AI の推測を実物で揺さぶる。「sandbox は普通にアクセスできている、そもそも curl が間違っていない？」「いやテナント管理一覧開いてるよ」（9 月）。
- 自分の環境側原因（トークンをいじったまま、確認対象テナントのずれ）を先に疑う。
- 内部エラーの生文言が利用者に見えていないかを確認する（「管理者ロールだから？それともクライアントでも見れちゃう？」）。
- 連絡文は責めないトーンで確認だけ（「軽く聞きたいので文章を作って」）。

## 観測頻度

93 セッション、月 20〜27 で一定。6 月は UI バグの協調デバッグ、7〜8 月は AWS 環境とデプロイ起因、9 月はローカル環境・CI・WAF が中心。
