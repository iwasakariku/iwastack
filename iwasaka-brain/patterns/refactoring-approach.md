> [!summary] TL;DR
> 棚卸し→置き場ルール→実行プラン→「順序は後で」。1 PR は小さく、フェーズ別・前 PR マージ後にベースから切る。
> 契約（API・生成コードが依存する名前）は不変、生成物や BE/FE は別コミット。
> 「分けすぎは本末転倒」と「本番前の最後の機会は思い切って」を使い分ける。

## いつ発動するか

本番稼働前の構造整理、機能別の監査、デッドコード・未使用依存の掃除、ルール違反の一掃、上流 OSS への追従。6 月は Web 管理画面を機能単位で監査するスキル（検査→壁打ち→計画→人間ゲート→実装→コミット→他 AI レビュー→スモーク→振り返り）を 10 機能回し、6 月末から API 側の層構造整理に移った。

## 手順・順番（観測されたもの）

1. **違和感から入る。** 「ここだけ enums があるのはおかしい？他にはある？」「ディレクトリ構成変？何が良い？」「ダラダラ書きすぎている感じもするし、他もこんなもんかという感じもする」と両論を添えて判断を仰ぐ。
2. **棚卸しを網羅で。** 複数の流派・表記揺れを grep で網羅スキャン、「読み取り専用で、編集前に報告」。インラインのマジック文字列が最大の散在源、のように事実を先に出させる（6 月）。
3. **置き場ルールを決めて実行プラン。** 「置き場ルールを決めて棚卸しして実行プランを作成、順序は後で」「対応順序は後で考えるので対応内容だけ」。
4. **計画群を統合する。** 「重複を削除しつつ未確定事項を fix、着手順の案を」→マスター計画→docs PR で先に確定（6 月）。
5. **スコープを小さく切る。** 1 PR 1 サブフェーズ、前 PR マージ後にベースから切る（共有編集を避ける）、生成物の再生成は別コミット、BE と FE は別コミット、docs と fix に squash。
6. **ゲートを固定して自走。** 自作の出荷スキル（型→テスト→lint→swagger→DI 起動スモーク→PR）が全緑なら自動で PR（6 月末）。
7. **成果を問う。** 「行数は減ったか」→構造移動フェーズでは減らない、という説明を受け入れる。「進め方的に P6 とか必要になってきそう？」と計画の延長可否を実コードで裏取りさせる。

## スコープ判断の基準

- 「分けすぎは本末転倒、一層足す程度」と上限を置く一方、本番稼働前の最後の機会として「安全寄りでなく思い切った Tidy First」を指示（6 月）。
- 「既存の参照実装も理想とは限らない、新卒と NestJS 熟練者の両方が良いとする形を」と OSS の実運用リポジトリ複数と比較させる。
- 契約は破らない。フロント生成コードが controller クラス名に依存するため controller 分割は契約破壊、と判定して「モジュール集約・契約完全不変」の案を選ぶ（6 月）。
- 上流追従は「丸ごと更新はオーバースペック・オーバーヘッドが大きい、必要な箇所だけ準拠」（8 月）。
- 「認知負荷最小・デグレなし・再発防止・トークン残量を意識していつ止めても損失が小さく」（8 月）。
- 削除は裏取り 3 点（import・SDK 利用・git 履歴）で真陽性を確定。「各候補タグの import 0 件を grep で実証」と誤除外防止を先に求める。
- 直らない規則は戻す。推測依存の参照列解決を 2 度変えても壊れたため、ブランチ前の規則に戻した（9 月）。

## 典型例

- **6 月・データ基盤**: 「これって使われている？」→「未使用を見つけるには？」→「knip は入ってそう、プランを」と段階的に広げ、AI の「未導入」訂正に lock ファイルの記載を指摘して正体を確認させた。
- **6 月・データ基盤**: 次の対象がコード量・テストコストともに桁違いであることを理由に、着手前の統括ドキュメント作成を指示。8 PR 分の学びを抽出してアーカイブ化し、スキルから参照させた。
- **9 月・データ基盤**: 「落ち着いた、レポートをまず」とファイル変更なしのレポートから着手。knip をインストールせずバイナリ実行で未使用依存と確信度を出させ、「knip 常設を立てて、wasm は DuckDB と同時、それ以外はそっちで」と作業の帰属を切った。

## 落とし穴・避けていること

- 修正の必要性自体を問う。「治すべき？直さなくても問題はない？」で実行時挙動に触れる修正と安全な修正を分け、安全な件だけ既存 PR に追加（7 月）。「指定しない理由がないと指摘が入っていて直すべきか検討したい、問題ないなら工数をかけたくない」（6 月、WMS）。
- 細かい修正コミットを独立させず本来の変更単位にまとめる。「ごちゃごちゃしすぎた」と自覚した時点で 14 コミットを 2 つに squash。
- 計画外の挙動変更にバグ候補が集中する（6 月の深掘り監査の結論）。構造移動と挙動変更を混ぜない。
- 自分で手を入れる前に「不要になったファイルを手で削除して報告」と並走の分担を明示する。

## 観測頻度

約 130 セッション。6 月（監査スキル 10 機能・API 構造整理のマスター計画）と 9 月（未使用依存・バージョン統一・移植後の整理）が山。7〜8 月は月 12〜24。
