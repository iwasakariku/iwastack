> [!summary] TL;DR
> スコープは着手前に明示し「これ以外はやらない」と書く。AI が勝手に広げた範囲は即座に戻させる。
> 束ねる基準は「同じ原因か」、分ける基準は「関心が違うか・方針が未決か・合意相手が違うか」。
> 見送ったものは捨てずに、別チケット候補・質問・PR 本文の未対応欄として必ず痕跡を残す。

## 原則の一文

やる・見送り・後回しを着手前に明示し、作業中に見つけた問題はその場で広げず「同じ原因なら束ねる、違う関心なら切り出す」で機械的に振り分ける。

## なぜそう考えるか

- AI は依頼していない変更（横幅、表示仕様、スコープ外の層）を混ぜてくる。放置すると差分が膨らみレビューと切り戻しが難しくなるため、「AI が勝手に広げた変更範囲は即座に戻させる」「AI のスコープ判断を鵜呑みにせず差し戻す」が繰り返し出ている（2026-06, 2026-07）。
- 壁打ちや監査の指摘に従いすぎるとスコープが膨らむ。「壁打ち結果に従いすぎず自分の判断でスコープを戻す」「自分の要望由来でもレビューで過剰なら戻す」と、スコープの最終判断を自分に置いている（2026-06）。
- PR は「1 つずつマージ可能」「レビュアーがマージ判断できる大きさ」を保ちたい。スコープ外の層や以前からある構造課題を同じ PR で抱え込むと、その PR のマージ可否判断が濁る（2026-06）。
- 一方で、同根のバグを別々に直すと設計がバラつく。「同一領域の関連バグは個別でなくまとめて設計を揃えて直す」「同根の未起票バグも 1 PR で潰す」（2026-06）。

## 具体的にどう現れるか

- **2026-06**: スコープは自動追記のみに限定し余計な機能を混ぜない。BE 変更は既存 PR に同梱せず別 PR に切る。以前から存在する構造課題は本 PR で抱え込まず別 PR に切り出す。来週は BE に手を出さずフロント 1 機能に専念する、と期間単位でも範囲を切る。
- **2026-06**: FE 監査中でも原因が BE なら BE を直してよいが、その場合はスコープ判断を先に明示する。似て非なる別設定（時間帯制限）は触らせない、と「隣にあるが別物」を明確に外す。
- **2026-06**: 小機能は P0/P1 に絞り、後回し項目は明示して積み残す。スコープ外の問題は別 issue 向けメモとして切り出す。気になった点はスコープ外でも質問だけはする。
- **2026-07**: スコープは最小に絞り不要な機能は明示的に除外する。一方「作業中に気づいた関連する不整合は同じ PR に取り込む」。スコープ外とした項目には理由を必ず問う。他者が担当する検査範囲には手を出さず自分の範囲だけ対応する。
- **2026-08**: 簡単な対策を先に入れ、構造的な対策は別課題に分離する。セキュリティ対応は高速化とは分離し、関連するインフラ側チケットに寄せる。チケットの射程は実態に合わせて広げる（1 入力形式から取り込み全体へ）こともある。
- **2026-09**: 計画書に「これ以外はやらない」と書く。方針未決の論点は実装から切り離し、決めることを先頭に置いた短い issue にする。残課題は親チケットに引き継ぎ、別 issue を乱立させない。試験用に作ったものは別チケットに切り離す。
- **2026-09**: 親 issue の範囲は「どのシステムに触るか」ではなく「誰の合意が要るか」で切る。実害のほぼ無い既存の揺れは単独チケットにせず次の PR のついでにする。
- **2026-10**: 同じ原因で直せる別チケットは同じ PR にまとめる。アップセル施策は事業判断なので別チケットにする。

## 例外・ゆらぎ

- 「迷うなら今回スコープに入れて片付ける」（2026-06）と「スコープ外で見つかった問題はその場で直さず別チケットに切る」（2026-09）が併存する。前者は小さく同型のものを、後者は関心の異なるものを指しているように読めるが、境界は一貫していない。
- 「レビューで見つかった横断的なセキュリティ改善は別チケットに切らず同じ PR で直すこともある」（2026-10）。セキュリティは優先度が高いため、スコープ原則より先に通す場面がある。
- 「小さな掃除は関連する実装 PR に同梱」「小さな追加修正は既存チケットに相乗り」（2026-08〜09）。小ささが明らかなら分離コストの方を嫌う。

## 観測頻度

6 月（AI 運用の立ち上げ期、約 25 件）と 9 月（課題管理の整備期、約 20 件）に集中。7〜8 月も毎月数件は出る。「別 PR に切る」「別チケットに切る」系が最多で、「束ねる」系がそれに続く。
