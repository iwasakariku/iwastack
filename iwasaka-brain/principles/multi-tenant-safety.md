> [!summary] TL;DR
> 境界は既定で閉じ、例外はローカルだけ。フロントのガードで安心せず API 側の担保を確認し、権限系の確認は一般ロールで行う。
> 「直す」前に「誰がどの経路で踏めるか」「直した後の攻撃面」を比べ、直す方が危ないバグは直さない。
> 本番データへの書き込み経路・本番環境への不要な操作は一切許容しない。

## 原則の一文

テナント越境と認可は「既定で遮断・ローカルのみ例外・API 側で担保・一般ロールで検証」を崩さず、修正の是非は到達経路と修正後の攻撃面を実測で比べて決める。

## なぜそう考えるか

- 扱っているのがマルチテナントの SaaS で、「データは境界を越えないが列定義は共有できる」という業務モデルを守ることが設計の前提になっている（2026-08）。
- 「他テナントのデータが見える可能性のある経路は既定で遮断し、ローカルのみ例外にする」「セキュリティの既定は厳しく保ち、ローカル環境だけ例外を許す」（2026-07）。利便性のための例外を本番側に持ち込まない。
- 認可は「フロントの UX ガードだけで安心せず API 側の担保を確認する」（2026-06）。見た目で塞がっていても担保とみなさない。
- 「性能改善の変更でもテナント越境の検証を必ず行う」（2026-07）。セキュリティと無関係に見える変更でも境界の検証を省かない。
- 「直す方が危ないバグは直さない」（2026-09）。修正が新しい攻撃面を開くことを警戒し、「自分の修正で新たに増えた脆弱性は同じチケットで解決するか修正自体を取りやめる」（2026-08）。

## 具体的にどう現れるか

- **2026-06**: 管理者でも選択中スコープに絞る。権限系スモークは一般ロールで行い、権限レベルの異なるユーザーで両方試してから結論を出す。危険操作のガード不足はすぐ直さず、まず調査して経営層へ懸念共有する。権限はいったんシンプルに統一し、拡張ポイントだけ残す。
- **2026-07**: 本番データへの書き込み経路は一切許容しない。認証関連の設定値を git 管理に入れる前に可否を確認する。計画書の段階でセキュリティレビューを通す。
- **2026-08**: 脆弱性は一般的な利用ケースに翻訳して理解してから対応範囲を決める。個別の穴を塞ぐ前に、破られた先で何を失うかを実測して優先順位を決める。監査で実測されたバイパスは即修正する。セキュリティレビューは変更が増えたら再実施する。認可バグは退行か生まれつきかの経緯を確認してから起票する。
- **2026-08**: 画面文言に認証基盤のベンダー名など実装詳細を出さない。一方、パスワード要件の明示は親切さが勝つと判断する。
- **2026-09**: 権限で見せ分ける情報は DTO の型として分離する。運用者の作業量はテナントに見せず特権者だけに表示し、一般ユーザーにも返る応答には運用情報を足さず専用 API に理由付きで足す。認証が取れないときは fail-closed にする。
- **2026-09**: 「危険な行がある」と「その行に到達する」は別として優先度を決める。「直す」前に「誰がどの経路で踏めるか」と「直した後の攻撃面」を比べる。発見には経路・必要権限・再現方法・確信度を必須にする。
- **2026-09**: テストユーザーのロールは画面要件から決める（最上位権限は偽陰性になる）。本番環境は調査目的でも触らない。認証の責任の置き場（自社が預かる資格情報か、顧客組織が発行する身分か）を意識し、外部企業の利用を前提に全社統一 IdP は採らない。
- **2026-10**: 各フェーズでコードレビューとセキュリティレビューを別のレビュアーで行う。認証情報はコードに書かず実行時に OS の資格情報ストアから読む。公開前・引き継ぎ前に秘密情報の混入を確認する。

## 例外・ゆらぎ

- 「認証が取れないときは fail-closed」（2026-09-18）と「権限不足時は失敗させるのではなく安全に従来方式へ戻す」（2026-09-28）が併存する。前者は認証そのもの、後者は追加機能の権限不足で、従来方式が安全と確認できる場合に限ってフォールバックしていると読める。
- 「監査指摘を鵜呑みにせず運用前提と照らして受容/対応を切り分ける」（2026-07）、「構造的に不可避なら根拠付きで受容を判断する」（2026-07）。すべて塞ぐのではなく、到達不能なものは背景として記録して終える（2026-09）。
- 「未知の利用者がいる経路は塞がず、再発防止のコメントを残す」（2026-07）。塞ぐことで業務を止めるリスクも天秤にかける。
