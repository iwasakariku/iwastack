> [!summary] TL;DR
> 速度を取るのは「契約不変・可逆・ローカル・暫定」の領域、品質を取るのは「振る舞い変更・本番・セキュリティ・デグレ」の領域。
> 「待たずに進む」ための道具（スタックブランチ、draft PR、暫定策、仮値）を多用し、未検証を痕跡で残して前進する。
> 場当たりの連続修正は禁じ、デグレ回避は速度に優先する。

## 原則の一文

変更の性質（振る舞いが変わるか・戻せるか・本番か）でレーンを分け、安全なレーンは止めずに流し、危険なレーンには検証フェーズを追加して時間をかける。

## なぜそう考えるか

- 「失敗が成功に見える状態は最優先で潰す」（2026-06）、「連続する不具合修正は場当たり対応を禁じ、根本原因と全体設計で直す」（2026-06）。短期の速度より、後から発覚する欠陥と手戻りの方を高コストとみなしている。
- 同時に「待ち時間を作らない」ことへの意識が強い。マージ待ちでは次に進む、動作確認前でも PR を出す、環境制約で止まるときは一時的な妥協で先に進む（2026-06）。止まることのコストも見ている。
- 両立の手段が「レーン分け」。契約不変かつゲート全緑の構造移動は確認なしで PR まで自動、振る舞いが変わる変更は PR 手前で止めてスモーク、リスクが高い変更は通常手順より深い検証フェーズを追加する（2026-06）。

## 具体的にどう現れるか

- **2026-06**: コスト最適化より開発速度を優先する（ビルド環境の判断）。マージ前提のスタックブランチで次に進む。契約（controller・API）を変えないリファクタはゲート全緑を条件に PR まで進め、ゲートが 1 つでも赤なら PR を作らず止める（緑を装わない）。
- **2026-06**: 過剰な巻き戻しより、ガードを足して前進する。触るなら本番稼働前の今しかない、という時機の判断を優先する。
- **2026-07**: 速度より考慮漏れ・デグレ回避を優先する。場当たり的な修正はせず、測定→1 つずつ検証→有効なもののみ導入でデグレを最小化する。対策は 1 つずつ適用して効果を確認する。
- **2026-07**: 使えない新仕様を待たず、現行仕様で直しつつ将来方針を文書化する。dev 環境で自然収束する実害小の問題は対策を見送り記録だけ残す。MVP では軽量チェック（警告のみ）に留める。スモーク未実施なら PR は draft にする。こまめに push する。
- **2026-07**: 柔軟性と失敗時の体験を優先して工数増を受け入れる。使いやすさをトークン効率より優先する。
- **2026-08**: いつ止めても損失が小さい順序で進める。チーム規模に合わせてまずローカル運用から始める。高重大度は全対応してからマージし、中・低も網羅的に洗い出す。動けば恒久実装は見送る判断もする。
- **2026-09**: 精度より判断に足る概算で良い。サービスイン当初は人が介在する前提で機能を削る。仮値で進めて細部は別課題へ切り出す。恒久対応までの間は機能を閉じる暫定策を先に打つ。顧客展開は担保ができてから、それまでは検証環境に留める。
- **2026-09**: 引き継ぎの優先順位を「品質・テスト・セキュリティ ＞ 新機能・UX」と明示する。時間枠の限界では無理に続けず途中状態を記録して中断する。分割のための分割は回帰リスクの方が高いとして避ける。

## 例外・ゆらぎ

- 「コスト最適化より開発速度を優先」（2026-06）と「速度より考慮漏れ・デグレ回避を優先」（2026-07）が併存する。前者は開発環境・ビルドの話、後者はプロダクトコードの修正の話で、対象が違う。
- 「動作確認前でも PR を出して前に進める」（2026-06）と「PR の前に必ずローカルで動かして確かめる」（2026-09）が併存する。前者は draft 前提、後者は Ready 前提と読める。「Draft かつチケット未採番の PR は Ready にしない」（2026-07）がその境界を示す。
- 「見積もりは安易に増やさない（追加修正があっても据え置き）」（2026-10）。品質のための追加作業を工数に転嫁しない姿勢で、速度側の規律として働く。

## 観測頻度
