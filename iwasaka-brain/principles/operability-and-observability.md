> [!summary] TL;DR
> 障害は「どの環境で・どのコミットが・どの防御層を通って動いているか」の事実確認から入り、生ログを加工せず貼って一段ずつ絞る。
> 沈黙を成功と誤認しない。エラーが出ない滞留は時間メトリクスで、デプロイ完了は digest 一致で、復旧は実体照合で確認する。
> 本番操作は AI に代行させず自分で行い、不可逆な操作は退避・バックアップを先に取る。コストは体感ではなく実測と公式料金で出す。

## 原則の一文

運用は「実体で確認できること」を増やす方向に設計し、観測できない状態（沈黙・緑に見える失敗・古いイメージの成功表示）を最も警戒する。

## なぜそう考えるか

- 「沈黙を成功と誤認しない（失敗シグネチャも監視する）」（2026-06）、「エラーログが出ない滞留は時間メトリクスで検知する」（2026-07）、「現行イメージが想定タグ以外なら失敗させ、古いイメージのまま成功に見えるのを防ぐ」（2026-09）。見えない失敗が繰り返し判断の対象になっている。
- 「障害の根本がデプロイ漏れなどの運用にあるなら仕組みで防ぐ」（2026-07）。障害を個別に直すより、運用経路そのものを整える。
- 「本番操作は AI に代行させず自分で実行し結果を貼る」（2026-08）、「本番調査は読み取り系の情報取得に限る」（2026-06）、「本番環境は調査目的でも触らない」（2026-09）。本番への接触は最小化し、触るときは自分の手で行う。
- コストについては「対策の前にコスト感を把握する」「0 円に見える案でも設計変更コストを見落とさない」（2026-07）。安く見える案の隠れたコストを疑う。

## 具体的にどう現れるか

- **2026-06**: ログ基盤は AI の作業を止めない（fail open）前提で組む。ログは加工せず生のまま渡す。リリース前に設定差分と反映先サーバーを全件確認する。運用の変更は手順書に反映して恒久化する。ダミーデータ投入は通常 seed と分離し、明示フラグでのみ動かし、非ローカル環境では動かないガードを入れる。
- **2026-07**: 障害調査ではまず対象環境に載っているコミットを確定する。実測の内訳で責任範囲（インフラかアプリか）を切り分けてから打ち手を選ぶ。暫定回避と本筋修正（インフラ側）を区別して扱う。コストはログの実測値から計算する。自分でも確認できる手段（接続手順）を手元に持つ。
- **2026-07**: 監視は使う予定のサービス前提で具体化する。本番と検証環境が別サーバーなら環境ブランチで一方向マージにする。エラーメッセージは利用者の自己解決を助ける文言にする。
- **2026-08**: CI の課金は実行時間を実測して許容範囲か確認する。コスト試算は公式料金ページを自分で確認して数字を出す。データ移行は必ずバックアップを取ってから実行し、移行後も旧データは消さず残す。古い状態は削除せず退避してから作り直す。
- **2026-08**: 復旧確認は digest 照合など実体で確定させる。障害時はまず設定・権限の確認から入り、裏に同種の反映漏れが無いかを横展開で確認する。流出の疑いがある鍵は失効・再発行する。依存更新は対象パッケージに限定し、フル update は避ける。
- **2026-09**: env は読み込み優先順位（誰が最後に勝つか）を把握してから直す。デプロイ経路ごとに何がデプロイされるかを把握する。ドリフトは原因主体（CD／手動／IaC）を履歴で特定してから直す。デプロイ中は lockfile や依存に触る作業を避け、読み取りだけの調査は進めてよい。
- **2026-09**: 定常デプロイに不要な重い処理は載せない。運用で使う SQL は内部 ID ではなく業務コードで対象を指定する。運用で API を直接叩く回避策は取らず画面機能として実装する。本番は小さくてもマネージドに寄せられるなら寄せる。デプロイ順序（API 先行）を引き継ぎに残す。
- **2026-09**: 月初限定のスケジュールは検証環境でサーバーが停止している時間帯があるので採らない。AI が読むコンテキストの重さを開発ペースの観点で見直す。重い処理はレート枠の境界を跨いで回し、枠を使い切る。

## 例外・ゆらぎ

- 「コスト最適化より開発速度を優先する」（2026-06）。開発環境のコストは速度の後ろに置く。
- 「dev 環境で自然収束する実害小の問題は対策を見送り、記録だけ残す」（2026-07）、「動けば恒久実装は見送る判断もする」（2026-08）。すべてを恒久対応しない。
- 「機能が無いなら当面は SQL で手当てし、恒久対応は issue に残す」（2026-09）。「運用で API を直接叩く回避策は取らない」と併存しており、SQL での手当ては許容しつつ API 直叩きは避けると読める。

## 観測頻度

障害対応・運用カテゴリの判断は全期間で毎月出る。7 月末（性能・インフラ切り分け）、8 月下旬（復旧・鍵・移行）、9 月中旬（デプロイ・ドリフト・WAF）に山がある。
