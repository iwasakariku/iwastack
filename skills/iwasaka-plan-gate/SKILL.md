# iwasaka-plan-gate（計画書策定と人間ゲート）

「実装前に計画書を書かせる型」（`patterns/plan-before-implement.md`）に基づく実行スキルです。
コードを書く前に現状と計画を突き合わせ、疑問と未確定事項をすべて潰します。

## 運用ルール

1. **実装と計画の分離**: 「まだ実装はしない」「コード変更はしない」を徹底する。
2. **工数は書かない**: 見積・工数は計画確定まで空欄とし、計画書にも記載しない。
3. **As-Is / To-Be は変わる時だけ**: 振る舞いや構造が変わらない部分に冗長な As-Is / To-Be を書かない。
4. **非目標（Out of Scope）を捏造しない**: 過去に確定した方針や、今回あえてやらないことを明確に切り分ける。

## 計画書の標準フォーマット

```markdown
# 計画書: [チケット番号 / 機能名]

## 1. 目的と背景
- 本質的な欲求 / 解決する課題を1〜2文で簡潔に（冗長な背景は禁止）。
- 参照したベストプラクティス / 既存コードの踏襲箇所。

## 2. スコープ
### 対象（やる・In Scope）
- [ ] 項目1
### 非対象（やらない・Out of Scope）
- [ ] 項目A（理由: 別チケットで対応 / 今回は不要）

## 3. 変更方針（Architecture / Design）
- 契約（API / DTO / Controller名 / DBスキーマ）への影響: [完全不変 / 拡張のみ / 破壊的変更あり]
- 既存パターンとの一貫性: どこを踏襲するか

## 4. 受入基準 (Definition of Done - DoD)
- [ ] 満たすべき仕様・契約
- [ ] テストで検証可能な仮説（実測条件）
- [ ] ロール別のアクセス権限（一般ロールで検証）

## 5. 実装ステップ
- Step 1: REDテスト作成 (iwasaka-red-tester)
- Step 2: GREEN実装
- Step 3: 独立レビュー 2巡 (iwasaka-reviewer)
- Step 4: スモーク確認
```

## 未確定事項の質問ファイル化

仕様分岐や不確実性がある場合、計画書の中に放置せず「質問ファイル」として切り出します。

```markdown
## 未確定事項（質問ファイル）

| # | 質問内容 | 選択肢 | 推奨案と理由 | ユーザー回答 |
|---|---|---|---|---|
| 1 | 既存データの移行要否 | A: マイグレーションで一括変換<br>B: 参照時にフォールバック変換 | A (整合性担保のため) | [未回答] |
```

- ユーザーは `1: A` や `推奨でOK` と即答できる粒度にする。

## 承認ゲートの通過ルール

- ユーザーからの承認合言葉:
  - **「計画OK」**: 実装フェーズへの移行を許可。
  - **「骨組みOK」**: 動作確認が今すぐできない場合、骨組み（walking skeleton）の実装のみを先行許可。
- 承認が得られたら、受入基準（DoD）をチケット/イシューに書き戻し、実装へと進む。
