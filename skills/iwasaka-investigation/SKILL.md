# iwasaka-investigation（調査・障害トリアージ）

「調査の進め方」（`patterns/investigation-flow.md`）および「障害・不具合対応の初動」（`patterns/bug-triage-and-incident.md`）に基づく実行スキルです。
推測を排し、事実と一次証拠のみを積み上げて原因を突き止めます。

## 調査の8段階手順

1. **症状＋仮説を一文で提示**:
   - 否定されてもよい前提で仮説を置く（例:「デッドコードなのかも」「旧イメージ残存かも」）。
2. **判断より先に事実を洗う**:
   - コードの利用箇所、参照元、関連する設定を網羅的にリストアップ。
3. **二択で問う**:
   - 「エラーが出なかったから？それとも繋ぎ込みができていない？」のように分岐を狭める。
4. **「どこに実装ある？」の経路特定**:
   - 画面 → サーバーアクション/ハンドラ → API/コントローラ → サービス層 → DB/外部連携 の呼び出しチェーンを確定する。
5. **実データ・実コマンドで裏を取る**:
   - ログの仕込み、テストデータ投入、SQL実行により、手元の環境で事象を実証する。
6. **横展開を問う**:
   - 「他にもそういう箇所はないか？」。修正対象ごとに「不要 / 予防的 / DRYあり」を仕分ける。
7. **理解できるまで掘る**:
   - 腑に落ちない説明があれば「図にして」「何かに例えて」と問い直す。
8. **範囲を区切る**:
   - 調査フェーズではコードを書き換えない。「一旦調査だけ、実装はしない」。

## 障害対応時の初動原則

- **生ログ・エラー出力を加工せず貼る**: 要約せず全文、スタックトレース、行範囲を示す。
- **初発か再発かを確認する**: 「この事象は今までもあったのか、今回が初めてなのか」。
- **時系列の整合を疑う**: 「前は動いていたなら、直前の変更だけが根本原因とは限らない」。
- **対症療法を拒絶する**: 「場当たり的に対応せず、全体を見通して対応して」「再発防止策もセットで」。
- **退避・バックアップを先に行う**: 破壊的コマンドの前にバックアップを取得し、旧データは即座に削除せず退避する。

## 調査レポートの標準フォーマット

```markdown
## 調査レポート: [調査対象 / 障害概要]

### 1. 結論（3行以内）
- 何が起きていたか（根本原因）
- 影響範囲

### 2. 確定した事実と一次証拠
- 事実A — 根拠: `ログ出力 / コマンド実行結果 / ファイル#L番号`
- 事実B — 根拠: ...

### 3. 原因究明の経路（Trace）
- 呼び出し経路: `Client -> Controller -> Service -> Query`
- 破綻した箇所と理由

### 4. 横展開と影響範囲
| 対象ファイル / 箇所 | 修正要否 | 理由 (不要 / 予防的 / DRYあり) |
|---|---|---|

### 5. 再現手順 (Reproduction)
1. コマンド / 操作手順
2. 期待される挙動 vs 実際の挙動

### 6. 未検証事項・残る仮説
- 【推測】項目と今後の確認方法
```
